# TeXScholar：供作者与 Codex 使用的论文写作规则

适用新论文、章节撰写、润色、图表说明、投稿准备和审稿意见回复。先读取真实源文件、作者顶部规则、局部注释及已有唯一审核状态。作者最新要求和既有项目规则优先；已安装的科研写作 SKILL 继续按需加载。本指南是可分享的通用起点，不包含作者的真实论文或私人全局 AGENTS。

## 科学与修改边界

- 不编造参考文献、实验数据、显著性、审稿人原话或已经完成的修改。项目实验结论必须有实际结果支撑；不足时标明 unsupported / needs experiment，不能用流畅表述冒充证据。
- 本地真实 .tex/.bib 是唯一正文来源。先改手稿的候选，再基于实际候选写回复；有充分依据的仅回复解释不强造正文修改。作者接收前正式正文保持不变。
- 普通候选按相邻修改位置组织，可含多句但最多一个自然段，不跨段；公式、图注、表注等特殊内容独立审核。同一位置综合多个审稿意见为一个候选，不按问题数创建重叠项。每个明确开始的新批次，正文从 1、回复从 a 编号；同批内不复用已发编号，返修沿用原号。固定长度的内部批次身份区分重号，重启不重排当前批次。
- 接收、返修请求处理、依赖新鲜度和科学问题闭合是不同状态。保存、排版、编译和 Git 都不是接收。不要在普通写作后自动编译，只有作者要求或实际布局核验需要时才编译。
- 插件的接收后自动更新审核 PDF 是独立显示偏好，默认开启、可在设置关闭；仅更新已有预览，不要求 AI 再手动编译或生成另一份 PDF。打开卡片、改候选、保存批注和拒绝不编译。审核颜色、删除线、间距和图例设置也仅用于显示，不向正式源文件插入颜色宏、不改变写作内容或投稿标记规则。
- 长期保存的是已接收并经 Git 备份的成果；未接收候选和批注是可替换工作数据。AI 重新出稿时用同编号 rework，可明确传 discard_annotations=true 重置旧批注，不要求作者先逐条接收／拒绝。元数据补关联则严格保留其他审核字段。具体关联接口、示例和全局 SKILL 合并要求见 [原始问题关联规则](question-linking-guide.md)。

## 写入源码注释，而不是新增跟踪文件

- 全篇长期要求保留在顶部 CODEX-RULES；目标、术语、总逻辑、风格和篇幅放唯一主文件顶部 CODEX-WRITING-PROFILE。审核决定和编号只进入已有唯一 CODEX-REVIEW-STATE，不增加第二份状态。
- 段落的目的、问题、依据、信息顺序、前后承接和待核验点，写在该段前的 CODEX-PARAGRAPH-PLAN 注释。回复的依赖和原问题来源写在对应回复前；公式、图表说明放相应独立环境前。
- 不创建 Markdown 任务表、问题映射 JSON、候选副本或项目管理垃圾文件。允许的本地审核对象和构建产物继续由既有工具管理，不另造索引。保留作者科研注释，不能笼统删除所有注释。
- 不把模板文件名写成全局依赖。提炼作者给出的参考论文／段落的写法与逻辑，转换为当前项目的中文局部计划；不复制参考中的事实、数值或不适用的结构。
- 新项目从未建立审核状态时，在作者授权的实际写作中才建立所需顶部注释、唯一状态拥有文件和起始计数；先核对所有实际主文档与回复信，不固定要求 main.tex，不为仅安装工具初始化论文。SOURCE-ONLY 检出可以建立新批次，从 1／a 开始，不伪造历史。普通继续工作复用当前批次；只有明确开始新批次才调用 begin，替换旧候选与批注。已接收但未备份的成果先完成提交推送；失败不清空。
- 新写或实质改写的普通正文一句一行，段内不插空行，段间空行。识别缩写、小数、数学和宏，不机械按句号分割，不全文件重排旧文本。缩进功能只改缩进，不重写行结构。

## 参考引导与整体逻辑

写全新论文或作者要求确认整体逻辑时，先检查现有内容与作者最满意的参考资料，讨论问题、挑战、方法、证据的对应方案，确认后再大段撰写。参考模仿包括句内、句间、段间和章节间关系，不是套用句式数量。正文通过具体内容自然承接，少用空洞的过渡套话；注释中明确逻辑，正文不把逻辑讲解重复一遍。

## 摘要

默认 180～210 英文词，上限 220 词；期刊明确要求优先。按功能组织，不强制固定句数：任务与必要性 → 关键问题及其后果 → 本方法的核心思想、必要机制及作用关系 → 实验证据与代表性结果 → 适用时的代码声明。问题是引言挑战的忠实缩写，不强制两类问题。方法介绍按实际因果或信息流展开，不按模块名逐个报菜名。

## Introduction

起始段由真实问题确定需要哪些背景，背景为凸显问题服务，不能为了介绍而介绍。句子各有实际信息：必要的任务或应用事实、真实约束、约束对现有能力的影响、由此需要解决的研究问题。表述顺序依参考与课题调整，不机械把“问题”塞在第一句。

已有研究通常按 2～3 类解决思路组织，说明各自解决了什么及仍存在的相关边界，而非堆论文。挑战通常 2～3 个，与真实创新点及后续验证一一对应；不提出本方法没解决的关键漏洞。方法总览逐项回应这些挑战，说明机制为何必要、输入输出怎样衔接。贡献忠实概括实际创新与证据，使用 `\item[\textbullet]`。段落过渡通过研究对象、能力边界或必要条件的变化隐含实现，避免重复总结和刻板“然而／因此”串联。

## Method

先给最小充分的任务定义与总体输入输出，再沿真实计算依赖介绍机制。每个模块以具体信息缺口或现有操作的不足建立必要性，随后直接给定义、公式或操作，再说明该操作产生什么且如何供下一模块使用。不为每模块重复背景、动机口号或同一总览。总览图、正文符号、公式和实现需一致；模块过渡由实际中间表示、约束或依赖驱动，而不是一句“为了进一步提高性能”。不能宣称“只有这个设计才正确”而没有证据或限定。

## Experiments

设置先保证比较可解释和可复现：数据划分、预处理、指标、训练与比较协议。主结果回答方法是否有效；消融分别检验核心创新点的作用与必要性，组合实验验证机制之间关系。按实际需要核查重复实验与均值标准差、统计比较、敏感性、失败情况、限制和效率。缺少的证据明示，不把已有数据包装成尚未做过的实验。

结果段围绕一个有依据的判断：相关比较及关键数值 → 具体观察 → 与设计或适用边界的联系。避免逐格复述表格、只说“明显更好”、重复方法描述或对未经验证的因果下定论。图表标题说明任务、比较和阅读方式；结论与图表、正文和回复信中的数值、术语保持一致。

## 图表、讨论与结论

框架图表达必要计算路径、模块接口和挑战对应关系，不凭好看增加不存在的支路。图例、颜色、箭头、缩写、符号和正文引用一致。定量图需要真实数据和清晰统计口径。讨论解释证据、边界和局限；结论概括已证明的结果，不引入新贡献。参考文献检索与格式核验应加载独立的文献技能，核对原始来源与真实出版信息，而不是由模型补全可疑条目。

## 回复信

保留每个原始意见、身份、编号和顺序。每个回复按需要组织简短致谢、直接回答、最小充分依据、实际修改及定位；不机械使用四个标题或每条都长篇感谢。多个意见可共用一处手稿修改，但每条回复都要回答自己的关键点。文中尚未接收的修改只能称草稿，不说已提交或已完成；页码行号须基于实际编译结果，未编译时用章节和标签。

致谢、认同、当前事实与现稿内容用现在时；已完成修改用现在完成时及其被动式；既有研究用过去时；未来计划才用 plan to / aim to / will。按句子功能选择，不统一整封信一个时态。保留作者约定的英文术语、模板和称谓。回复与手稿在术语、范围、证据、摘录和定位上同步，实际源文件变化后重新核对受影响部分。

## 原始问题关联

在对应回复前的现有局部注释区写 `% CODEX-RESPONSE reviewer=R1-Q2 changes=1,3` 表示正文依赖；不要在此复制审核决定。需要插件查看原始意见时，同处写一行：

```tex
% CODEX-QUESTION {"id":"R1-Q2","file":"reviewer-comments.tex","quote":"Exact original reviewer wording."}
```

文件名只是格式示例，不要求创建该文件。`file` 指项目内真实原始意见的相对路径，`quote` 保留真实源码内容和换行，且必须唯一匹配。当前精确跳转支持 UTF-8 .tex / .txt / 已有 .md；PDF、Word 原件不伪造段落定位。编号保留作者约定，不由正文修订 ID 推导。为相关候选调用 propose / rework 时，在 `questions` 数组传入同样对象，保存在已有唯一状态中。一个候选可对应多个问题；未提供关系时显示未关联，不猜测。不得为导航生成一套新问题表。

## 每批成果

只有作者明确说本轮审核完成／本批审完，或按结束审核按钮，才备份本批已接收成果。提交说明含目的、相关编号和文件范围；核实已授权私有 GitHub 后正常推送，保留手动暂存，不夹带未接收候选、批注或无关提交。推送成功才按既有工具的锁和引用校验精简已完结历史、删除获准的无引用对象缓存；推送失败不清理，不把成功备份当科学问题解决。工具维护和安装插件不操作真实论文的 Git、状态或缓存。

## AI 的工具入口

本指南同目录包含 `source_review.py`、`review_checkpoint.py` 和 `backup.js`，不依赖个人 SKILL 安装目录。先读取工具帮助及真实源文件／唯一状态；状态修改通过其 `--apply --expect <当前拥有文件 SHA256>` 和 UTF-8 JSON stdin 入口，不手改压缩 DATA 或对象文件。写新候选用 propose，返修用 rework，作者明确接收才 decide。先预览操作范围；编号和候选必须以实际返回为准，失败不能声称已保存。未决批注和源文件局部注释是继续工作的依据，不靠聊天缓存或额外跟踪文件。
