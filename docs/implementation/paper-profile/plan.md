## 已查明的缺口

1. “识别／确认论文文件角色”仍在命令面板、src/document_roles.js:134注册。任务助手只走任务→项目→范围→补充→预览，没有角色复用/调整步骤，项目文件范围还是单选；任务附件让AI稍后读file_roles，不能代替用户可见的角色确认。v0.9.59到v0.9.60相关文件无差异，现有有限历史不证明近期删掉过该流程。用户当前宿主未实测，不能归因未重载。
2. CODEX-FILE-ROLES仍是角色权威，含逐文件多角色、编译入口、结构和角色登记owner；文档仍要求从CODEX-RULES/WRITING-PROFILE及局部注释读约束。安装不自动迁移源文件。单删顶注会丢角色确认并触发拒绝/再次提示。
3. 现有paper_background.py的SQLite已有papers(id,revision,entries)、aliases(root,owner,paper_id)、personal。P条目仅支持kind/text/evidence/source，完整数组替换和revision CAS；可承载论文约束/背景，不能把机器角色藏进文本。alias中的owner是审核状态位置，不是角色登记owner。
4. 当前P CLI先read_context找审核owner，read_context先scan源角色；直接让新角色读取依赖此CLI会循环。须基于已验证注册项目及既有paper_id先查资料，再读取上下文；未建审核批次也应能确认论文角色。
5. `% TS-BLOCK-BEGIN id=<UUIDv4> kind=<paragraph|display|slot|question>`及对应END是实际固定定位符，须成对保留。旧嵌入DATA/NEXT、迁移提示、SOURCE-ONLY头、旧颜色或位置批注各有不同消费者，不能一律视为废弃。现有迁移会保留部分头部，不等于清除工作稿；投稿导出只生成外部副本。

## 拟实施范围

### 1. 一份论文资料，结构化角色与有范围的规则

复用现有P数据库、paper_id及身份关联，在同一论文实体下保存结构化角色记录：真实相对文件及roles、编译root或null、结构基准、角色登记owner与确认状态。背景/规则仍用现有条目语义，保留来源、待确认事实和局部适用范围。采用现有事务/CAS扩展负责字段，保证角色编辑不覆盖背景、背景整组保存不覆盖角色，旧条目原样保留；不另造项目JSON、候选历史库或第二份权威。

从可信注册根及明确已有身份解析paper_id，区分审核owner与角色owner；同名不同根隔离，多根先选择，移动/跨owner只用现有明确关联且核冲突，不猜文件名或活动焦点，不把空记录当无旧资料。未创建审核批次不得为了确认角色自动开批。新资料确认接管后为唯一权威；旧未迁项目按原契约只读识别、标明待迁，不启动时暗写或自动删源块。重复/冲突权威或中断不得默默择一覆盖。

用户沿既有论文资料/角色入口编辑；AI通过受支持的结构化接口读取、按明确作者意图和revision修改并读回。既有owner不可随意搬迁、路径/链接/结构检查、编译未指定/不参与编译、信任与脏稿保护继续有效。个人U和公共S不因论文迁移而写入。

### 2. AI助手接通场景、角色和多文件范围

任务→真实项目→显示已确认文件角色/编译入口→“使用现有角色”或“调整角色”；未确认或结构变化时进入原角色确认能力，可取消。任务范围按实际场景允许多文件多选，显示真实角色并供作者调整；场景只作可见建议，不猜文件角色，不以任务范围修改项目角色。角色明确保存后再取消任务，仅取消任务，须如实说明已保存的角色仍保留。

选择结果真实写入附件/请求，预览后加入输入区，不自动发送。保留选区快速入口及配置安装分支的原意，必要角色缺口可见，不强迫无关写作目标或把配置任务当论文改写授权。旧命令ID和独立角色入口继续可达。

### 3. 接齐所有真实消费者

document_roles扫描/保存/启动通知、mcp_setup任务及资料编辑、mcp_server上下文/角色写前检查、inline_review编译入口统一读取论文资料；auto_backup独立Python进程由可信宿主传正确profile/项目身份，读不到不得放宽新增文件权限。source_review继续拒绝候选混入/修改待迁旧块，保持精确身份/锁/CAS/源保存事务。

ai_context及writing/collaboration/question指南统一说明作者确认的论文约束、局部范围与证据，背景参考事实不等于操作授权；任务、read_context/read_feedback与反馈附件都取得当前资料，缺失/冲突/旧连接明确可见。角色确认、AI写入与激活不再向已迁源顶插旧块。

备份/导出仍保持现有安全边界，不把私有SQLite或候选历史自动上传；明确源码备份不等于论文资料备份，同profile跨版本持久保留，跨电脑/新profile不声称自动可用。一次性迁移前必须有可恢复的本地资料与源保护安排；不为此擅建云同步、导入导出平台或上传私人资料。

### 4. 一次性迁移真实稿件，由总控协调执行

不新增清理按钮/向导/常驻迁移服务。唯一真实目标由用户明确为D:/Overleaf/TMI-DA-Marked-up Copy，不遍历或迁移其他论文。必要产品读写链完成并验证后，核定该路径实际根、两类owner、真实状态/角色/现有P及revision、脏缓冲/草稿、未备份成果和stage；发现链接、不同真实根或身份矛盾时只暂停相关对象。当前尚未读取真实稿件，后续不得以已有路径替代身份和状态核验。

将可靠识别的旧插件注释逐项映射到角色字段、论文约束/背景或仍需保留内容，保留原意、适用位置和来源；不得只用AI概括替代原要求。先CAS合并并读回现有完整资料，核下一上下文和角色/编译消费者确能读取，再在准确源版本及原writer/锁保护下移除已迁旧插件块和确证过时标记，保留当前TS定位符。普通作者注释、正文/公式、上一版及暂留批注、候选/问题/计数/依赖、未保存稿/用途和范围外stage不动。

所有旧版未决批注须先建立迁移前后对应关系，核原文、条目/版本/位置、用途/方案范围、关联问题和未处理状态，数量及内容与身份逐项核对；不能只看总数相等。旧内嵌DATA、位置批注或颜色承载的未决要求若需转换，须先证明转换后的独立审核项完整且可见可用，才能去除旧编码。若尚未有无损迁移能力，保留原痕迹并停止该部分，不为编辑区整洁牺牲任何未决批注。恢复/续审不得触发默认解决、开新批覆盖、旧批注裁剪或误把同文不同位置批注合并。
