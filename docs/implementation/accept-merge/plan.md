## 最终业务行为

1. 工作台保存当前原文后，使用现有队列协调受影响候选，再确立新展示基准；安全变化自动生成对应新版本、保留旧版及批注，重叠/歧义保留双方并明确冲突。普通 refresh 不能吞掉待协调源变化；接收自身源事务仍不重复生成版本。处理期间暂存的同步结果保留来源和精确版本集合，旧结果不能覆盖新状态或丢草稿。
2. 接收始终绑定点击时的 repo/owner/ID/version/option/页面实例。复用受控 decide 的已提交回执、更新后的状态/目录及下一项卡片，先减少紧接的重复读取，再复用未变化不可变候选版本的差异结果。缓存只复用确定不变的原文/方案计算，不能拿旧源定位、旧状态/草稿或旧决定当最新。优先现有对象版本、回执和队列，不新增常驻 Python、通用缓存框架或依赖。
3. 必须完成正式源保存、作者决定 finalize、相邻/同块未决位置维护和事务/CAS检查，才能显示成功并按当前流程跳转。保留筛选/目录/作者选择，处理期间后来的显式导航不能被过时自动跳转覆盖；不得接收下一项。草稿、延期批注、冲突及原有部分审核用法保留。批量仍一次完整预检和受控事务，不能串行调用单项来伪装真正批量。
4. PDF、Git保持后台；它们的网络/编译/备份不进入接收成功等待，失败不能回滚已成功决定。正常后台任务与前台事务的共享锁保留。如受控完整队列证明保存事件在审核锁期间导致备份失去工作，复用实际审核完成/队列事件续接，不无锁写、不加无依据定时重试。
5. 保存型备份在捕获并核验的源码版本上，记录本次确已包含的 accepted ID/version、源快照与 Git 文件树/commit 关系；仅远端核实成功后，作为显式新批次门的发布证据。其后才接收的版本不被旧回执放行；仅本地提交/推送失败仍阻断。不能把 Git commit 塞入旧源码 snapshot/done 字段。普通自动备份不接收、不精简、不清候选、不自动开新批次；原“完成审核/精简”继续独立主动整理，用户不必为已成功的备份再点一次说明/清理流程。
